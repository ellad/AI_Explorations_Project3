**Agent:**

I ordered the checkpoints by dependency, risk, and the need to keep each stage testable.

1. **App foundation first**
   The semantic page structure, CSS foundation, test setup, and deployment configuration give every later feature a stable place to live. Setting up GitHub Pages early also exposes path and module-loading problems before the app becomes complex.

2. **Location data before weather integration**
   Open-Meteo needs coordinates. Therefore, city search, ZIP lookup, and device location must reliably produce a selected location before the complete weather flow can work. Census processing is also a substantial technical risk, so it should not be postponed.

3. **Weather retrieval before recommendations**
   The recommendation engine should consume normalized app data, not raw provider responses. Creating and testing the Open-Meteo normalization boundary first keeps provider-specific formats out of the rules and interface.

4. **Recommendation rules before visual rendering**
   Temperature categories, reminders, notices, timing, and incomplete-data behavior determine what the interface must display. Testing these as plain JavaScript makes errors easier to isolate than testing them through the finished UI.

5. **Variation logic before the complete outfit artwork**
   The specification requires 108 outfit slots, deterministic initialization, independent reminder wording, and in-visit restoration. Defining and validating that structure first establishes exactly what the SVG system must support and prevents creating artwork that cannot be combined correctly.

6. **Artwork begins early but integrates after its contract is known**
   Artwork is one of the largest workloads, so concepting and asset production should begin alongside the early technical work. Final integration comes after the outfit matrix defines names, compatibility tags, anchor points, and layer order.

7. **Main interface after the underlying states work**
   Once location, weather, recommendations, variations, and assets have stable interfaces, the main screen can render one shared recommendation state. This reduces the risk of separate components inventing their own weather logic.

8. **Information screen after actual behavior is established**
   Its privacy, storage, data-source, AI-use, and asset disclosures must accurately describe the implemented app. Building it too early could leave claims that later become inaccurate.

9. **Accessibility and responsive refinement after integration**
   Semantic accessibility is included from the beginning, but full keyboard, screen-reader, contrast, zoom, phone, and laptop verification requires the complete interaction flow. This checkpoint is refinement and auditing—not the first time accessibility is considered.

10. **Full local verification before deployment**
    Component tests are run throughout the build. The later requirements audit checks the assembled system and catches interactions that isolated tests cannot.

11. **Deployment before usability testing**
    Peer testing should use the realistic HTTPS version on actual devices. This also exercises geolocation, production paths, network behavior, and browser differences.

12. **Usability revision near the end**
    Testing must evaluate a complete working version. The selected improvement is then implemented, verified, and redeployed as the final development checkpoint.

13. **Delivery audit last**
    Credits, disclosures, credential checks, transcripts, and the debrief depend on knowing the app’s final behavior and assets.

The central dependency chain is:

`location → normalized forecast → recommendation state → variations/outfit matrix → rendering → deployed usability testing`
